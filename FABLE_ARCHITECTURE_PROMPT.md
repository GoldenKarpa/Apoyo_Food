You are acting as lead architect for **Apoyo Food** (working subdomain `food.apoyolime.com`), the newest vertical joining the **Apoyo ecosystem** — a family of platforms helping Spanish-speaking immigrants in Trinidad build reliable income through digital tools. Sibling verticals already live: **Apoyo Salon** (independent beauticians), **Apoyo Portal** (cross-vertical claims/scheduling service), and the **Provider Client App / the Apoyo-Demia app** (Demia + Social, shared identity issuer). Apoyo Food does the same job for independent food creators — home cooks, bakers, dessert makers, caterers, and similar entrepreneurs — but the platform is explicitly **not** a delivery/logistics company (not Uber Eats/DoorDash/FoodPanda). It's a discovery-and-relationship marketplace: sellers showcase their work and get discovered; delivery/pickup/meet-up logistics stay entirely between seller and customer.

## Locked decisions for this planning session (don't re-litigate these)

- **Ecosystem integration: full, from day one.** Food joins the Apoyo-Demia app identity/auth, the portal membership registry (`VerticalMembership`), and — when relevant — cross-vertical reputation (rating events published to portal-core per the E7 foundation-program direction). Design Food's auth as "central issuance, local JWT validation, no visible redirects," the same model Salon uses — not a standalone auth system to be migrated later.
- **Payments: cash/offline only, for every phase covered by this plan.** No online payment processing (Stripe or otherwise) — matches Idea.md's own "Future Features" list explicitly deferring "Online payments." Seller and customer settle at pickup/delivery/meet-up. Don't design a payments module now beyond leaving room for one later.
- **Stack & hosting: match ecosystem convention exactly.** Next.js + Prisma + Postgres 16, deployed to the shared `srv1017419` VPS as `food.apoyolime.com`, on the non-root `user-pm2` daemon (per E2), with its own nginx drop-in following the documented include-glob pattern. Own git repo (this one, `Apoyo-Food`), own Postgres database + role (with the `GRANT ALL ON SCHEMA public` step VPS_INVENTORY.md flags as easy to miss).
- **Launch status: zero real users.** Like every other vertical was at its foundation stage — favor clean architecture over backward-compatibility shims; breaking changes during this build are free.
- **Media storage: object storage + CDN**, not local VPS disk — an S3-compatible bucket (e.g. Cloudflare R2, Backblaze B2, or AWS S3) with a CDN in front. Photography is core to the product's Airbnb/Pinterest-style design direction, so this shouldn't be an afterthought or a later migration.
- **Location model for MVP: an area/region picker**, not real geocoding — sellers and customers select from a list of Trinidad areas/regions (e.g. Port of Spain, San Fernando, Chaguanas, ...). This gives coarse "nearby" support cheaply. Precise lat/long geocoding (Google Maps/Mapbox) is explicitly a **later phase**, not MVP — design the schema so it can be added without a rework (e.g. don't hard-code area-only assumptions into core models if a coordinate field can sit alongside it cheaply).
- **Seller verification/vetting: deferred to a later phase.** MVP sellers self-register (mirroring how Salon's providers initially onboarded); formal vetting (health permits, ID checks) is a later architectural phase — note it in the plan but don't block the MVP slice on it.
- **Reviews/ratings: deferred to a later phase**, not in MVP. MVP focuses on browsing/discovery/Stories/ordering; reviews (and their eventual tie-in to portal-core reputation events per E7) come once there's real order history to review.
- **Product name: "Apoyo Food"** (not "Apoyo Cocina," despite Idea.md's title — use Apoyo Food consistently throughout the plan).

## What must be true of the earliest demoable slice (MVP)

This is the most important structural instruction: **design the full architecture for the whole vision in Idea.md, but sequence the phases/slices so the earliest phases produce an aesthetically polished, demoable MVP — not a scaffold with placeholder UI.** Later phases should layer in the more advanced/operational features. Concretely, the MVP slice(s) must include, fully realized (not stubbed):

- **Seller profiles + meal browsing + discovery** — the core browse experience: seller profiles, meal listings, category/discovery browsing, with the premium Airbnb/Pinterest/Instagram-inspired visual treatment Idea.md calls for (beautiful photography, generous whitespace, premium typography, large cards, mobile-first, PWA). This is the heart of the demo and should look and feel finished, not a wireframe.
- **Stories** — the Instagram-style ephemeral engagement feature. Visually important for the demo even though it's an engagement layer rather than core transactional function.
- **Ordering/booking flow** — pickup, seller delivery, meet-up — simplified (no online payment, no delivery routing) but a real, working request-to-order flow end to end.

Explicitly **out of the MVP slice**, planned for later phases instead:
- Seller dashboard + business insights/analytics (orders, followers, popular meals, profile views, repeat customers — and especially the anonymized demand-insights feature). Valuable, but phase-2-and-later seller tooling, not a customer-facing demo highlight.
- Reviews/ratings (see above).
- Seller verification/vetting (see above).
- Online payments, subscriptions, gift cards, loyalty, referrals (already in Idea.md's own "Future Features").
- Precise geocoding-based "nearby" (starts as area/region picker, upgrades later).
- Customer requests board ("need birthday cupcakes," etc.) — use your judgment on which phase this belongs in based on how much it depends on features not yet built (e.g. seller response/notification flows); call out your reasoning if you place it earlier or later than the above list might imply.
